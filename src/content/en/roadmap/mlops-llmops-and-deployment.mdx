## Overview

**Deployment** is the process of moving a trained model or AI application into an environment that users or other systems can access. It involves more than copying a model to a server. The application also needs to accept valid inputs, produce consistent results, make issues easier to detect, and release new versions in a controlled way.

**MLOps (Machine Learning Operations)** is an engineering approach to making the development, deployment, monitoring, and updating of machine learning models repeatable and manageable. It connects model development with the work required to operate models in production.

Operational approaches for managing large language model systems in production are commonly called **LLMOps**. The term can have different scopes across teams and products; here, it refers to operating LLM-based systems in production.

## Deployment and MLOps

This section covers the packaging, serving, release, monitoring, and maintenance work required to use a model in production.

### Model Artifacts and Serving Contracts

A **model artifact** is a saved model file or package created at the end of training. It may contain model weights or a serialized model object. To keep predictions consistent with training, the artifact should be considered together with the code that produced it, feature order, preprocessing steps such as encoders and scalers, and related configuration.

The rules that define which inputs an API accepts and which outputs it returns form its **serving contract**. For example, the API contract can specify required fields, data types, accepted values, and responses for invalid requests. If the feature order or preprocessing used in training differs from what is applied in production, the model may produce incorrect predictions without raising an error.

Validating requests against a schema and defining expected ranges, categories, and missing-value behavior for important inputs can help. An invalid request can be rejected or directed to a controlled fallback, depending on the system design.

### Serving Patterns

The serving approach depends on the use case, request volume, and acceptable response time:

* **Batch prediction:** Many records are processed together at scheduled intervals. Daily recommendation lists and periodic risk scores are examples.
* **Real-time API:** A prediction is generated when a request arrives. This can suit applications where users need an immediate response.
* **Asynchronous processing:** Long-running jobs are placed in a queue, and the user or another service checks their status later.

Packaging an application and its dependencies in a **container** helps it run consistently across environments. An API layer can validate inputs, call the model, and return results in a defined format.

### Versioning, Release, and Rollback

To identify the source of a production issue, track which versions of the code, model, data schema, preprocessing steps, and configuration are in use. Recording these components together also makes it easier to return to a previously working version.

A new version can first be tested with sample inputs in a test and staging environment. Traffic can then be shifted gradually. For example, a small portion of user requests can be sent to the new model first. A **rollback** plan describes how to return to the previous version if the new release causes an unexpected rise in errors or latency.

Deciding before release which indicators to monitor and when to pause a rollout makes release decisions easier. These indicators might include API error rates, response times, or a metric tied to the application's business goal.

### Monitoring and Data Drift

**Monitoring** means regularly tracking model and service behavior in production. In addition to checking whether the server is running, teams can monitor request errors, response times, missing or unexpected inputs, and prediction distributions. If actual outcomes become available later, model quality can be evaluated as those labels arrive.

**Data drift** is a change over time in how production inputs are distributed compared with the training data. **Concept drift** is a change in the relationship between inputs and targets. For example, changing user behavior may cause the same features to become associated with different outcomes.

A change in a metric does not automatically mean the model needs retraining. The data quality, feature pipeline, application rules, and model outputs can be examined together first. When true labels arrive with a delay, it can also help to track technical metrics separately from model quality metrics.

### Capacity, Security, and Privacy

To serve the expected request volume, account for peak concurrent requests, model memory requirements, and limits imposed by dependent services. **Load testing** with realistic input sizes and concurrency helps reveal the system's capacity limits in advance.

Access controls and limits on request and input size are also part of service design. Logs are useful when investigating issues, but personal or sensitive data should not be retained without a need. Access permissions, encryption, and data-retention periods can be considered during system design.

### MLOps Workflow

The model lifecycle does not end when training is complete. Production results and feedback help determine whether the model or data pipeline needs further work. When a change is needed, the first step is to investigate whether the issue comes from the model, the inputs, or the data pipeline. If a new model version is prepared, it can be compared with the current version using the same evaluation criteria before deciding whether it is ready for release. Recording these decisions and the versions involved keeps future updates traceable. Development and production then become connected parts of a feedback-driven process.

## LLM Deployment and LLMOps

In LLM-based systems, prompts, retrieved context, and tool configuration can also affect responses. Serving and evaluation therefore need to account for these components as well.

### LLM Serving and Optimization

Cost, memory use, and response time are considered together when serving LLMs. Common optimizations include:

* **Quantization:** Storing model weights at lower numerical precision can reduce memory requirements. Its effect on response quality depends on the method, so it should be measured on the target task.
* **KV cache:** During token-by-token generation, key and value tensors calculated for earlier tokens are stored for the duration of the request. This avoids recomputing the same values for the full history at each step; the added memory use should be considered when planning capacity.
* **Batching:** Processing multiple requests together can increase overall throughput, but it can also affect the wait time for an individual request.

A **cache** can reduce model calls by reusing a previously generated response when appropriate. **Semantic caching** attempts to match requests with similar meanings, not only identical text. A poorly chosen similarity threshold can return an unsuitable answer, so freshness and user permissions should also be considered when matching requests.

**Model routing** sends a request to a model or service based on the task. Simpler requests can be sent to a smaller model, while more difficult tasks can go to a more capable one. Routing rules should be evaluated for their effects on quality and cost.

These methods are not necessary for every application. The appropriate options depend on measurements of response quality, memory, cost, and latency under the target workload.

### Prompt, Model, and Application Versioning

Even when the model stays the same, a change to the system prompt or generation settings can change its responses. It is useful to record the model identifier, prompt template, generation settings, and tool configuration used in production together.

In RAG systems, the document collection, chunking method, embedding model, and search index can also affect responses. Tracking changes to these components makes it easier to investigate whether a change in quality came from the model, the prompt, or the retrieved context.

### LLM Evaluation

An evaluation set of task-relevant examples can be used to assess LLM responses. Correctness, adherence to the requested format, grounding in sources, and safety can be examined as separate criteria.

Running the same evaluation set after a model, prompt, or RAG change helps reveal regressions in examples that worked well in the previous version. Automated metrics may not reliably assess every response, so human review can be included in higher-risk use cases.

### Cost and Latency Monitoring

In addition to general error and response-time metrics, LLM services can track token usage and cost per request. **p95 latency** is the response-time threshold within which 95% of requests complete; it helps surface slow requests that an average can hide. Time to first token and the share of requests served from cache can also help explain the user experience and system capacity.

Considering these measurements alongside evaluation results helps show how a cost-saving change affects response quality. An operational guide that describes who takes which steps when a threshold is crossed is called a **runbook**. For example, it can describe checking the active version, changing traffic routing, or returning to the previous version when the error rate rises.
